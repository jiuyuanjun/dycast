## 1. P1｜已登录仍提示"要登录"，不能直接进弹幕界面

### 1.1 现状链路（实读代码）

```
login.rs extract_douyin_sessionid（WebView CookieManager 取 sessionid）
  → LoginWebviewPage.vue:56 每 2s 轮询，拿到就 handleLoginSuccess(:69)
  → store.setSessionid(sid)（store/index.ts:532）
        ├─ setProxySessionid(sid)  → Rust set_sessionid → 代理注入 cookie + warmup
        ├─ getMeInfo()             → 失败只 console.warn，state.user 保持 null
        └─ saveSession(sid, state.user)  → localStorage
  → App.vue:22 冷启动 restoreSession()（store/index.ts:564）
```

### 1.2 关键证据

- `store/index.ts:627`　`isLoggedIn = !!state.sessionid && !!state.user` ← **双条件**
- `store/index.ts:633`　`hasLoginRecord = !!state.sessionid` ← 单条件
- `store/index.ts:536-550`　`setSessionid` 里 `getMeInfo()` 失败 **只 warn，不回滚**，但 `state.user` 停在 null
- `request.ts:240-243`　`status_code !== 0` 时 **reject 一个字符串**（非 Error）
- `RoomConfirmPage.vue:77`　`router.push(hasLoginRecord ? '/live' : '/login')`
- `LoginPage.vue:7`　"登录抖音账号后才可显示礼物信息"
- `LivePage.vue:49/52`　礼物页用 `hasLoginRecord` 判定，否则显示"登录抖音账号后才可显示礼物信息"
- `tauriBridge.ts:86-90`　`withProxyOrigin` 在 `getProxyPort()` 返回 null 时 **静默返回裸路径**（不重试）

### 1.3 根因假设（按可能性排序）

1. **冷启动端口竞态（最高）**：`App.vue:22` 未 await `restoreSession()`；若此刻代理端口还没就绪，`withProxyOrigin('/dylive/...')` 返回裸路径 → 请求打到 `tauri.localhost` 而非 `127.0.0.1:<port>` → `getMeInfo` 必然失败 → `state.user` 为 null → 一切"已登录"判定失效。
2. **`state.user` 依赖网络成功**：即使用户确实有 cookie，只要 `getMeInfo` 一次失败，`isLoggedIn` 就是 false。
3. 用户看到的"要登陆后才能获取消息"在代码中**不存在原文**，最接近的是 `LoginPage.vue:7` / `LivePage.vue:52` 的礼物页遮罩文案，或 `ChatInputBar` 输入框被 disabled 的错觉。

### 1.4 修复方案

| 步骤 | 动作 | 文件 |
|---|---|---|
| A1 | 登录判定统一为 `hasLoginRecord`（有 sessionid 即视为已登录）；`isLoggedIn` 仅用于展示昵称/头像 | `store/index.ts`、`ChatInputBar.vue`、`LivePage.vue`、`LandscapePage.vue` |
| A2 | `withProxyOrigin` 增加端口就绪重试（最多 10 次 × 300ms），彻底消除裸路径请求 | `utils/tauriBridge.ts` |
| A3 | `secUid` 懒补齐：发送前若 `secUid` 为空，实时调 `getMeInfo()` 补一次再发 | `core/sendMessage.ts` 或 `ChatInputBar.vue` |
| A4 | `restoreSession` 增加"不因单次失败清登录态"的硬约束（现有 catch 已保留状态，需补：`code!==0` 分支不要清） | `store/index.ts:583-586` |
| A5 | 加诊断日志 `[Auth] sessionid=? user=? secUid=?`，便于实机定位 | `store/index.ts` |
| A6 | 文案改正：未登录→"未登录，请先登录抖音账号"；有登录记录但资料未取到→不阻断 | 各页面 |

### 1.5 需实机取证（1 条）

打开控制台页看是否有：`[Request] fetchLiveInfo => http://127.0.0.1:<port>/dylive/...`
- 若是 `…tauri.localhost/dylive/…` 或没有端口 → 假设 1 成立。

## 2. P2｜发消息提示"请登录直播间"

### 2.1 证据（已定位，高置信）

- `sendMessage.ts:41`　`if (!secUid) return { ok:false, msg:'请先登录抖音账号后再发送弹幕' }` ← **用户看到的就是这句**
- `ChatInputBar.vue:116-120`　调用时传 `store.state.user?.secUid`
- `store/index.ts:545 / 578`　`secUid: res.data.uid || undefined`
- `request.ts:291`　`uid: data.sec_uid || ''`

**结论**：`state.user` 有值（isLoggedIn 可能为 true，输入框可用）但 `secUid` 为空时，点发送必然得到"请先登录…"。`sec_uid` 取值路径与抖音实际响应不匹配（或该接口未返回）是直接原因。

### 2.2 修复方案

1. **先取证**：加一行日志打印 `getMeInfo` 的原始响应 `sec_uid` 是否存在（`request.ts` 内）。
2. 若确认字段缺失：改为多路径兜底取值 `data.sec_uid || data.user?.sec_uid || data.sec_user_id`。
3. **兜底不阻断**：`secUid` 为空时，改用 `friend`/`room/chat` 接口可接受的替代标识，或至少给出准确提示"登录资料未就绪，请重新登录一次"。
4. 与 A1/A3 合并实施（同一处代码）。

## 3. P3｜贡献榜数据不显示

### 3.1 数据链路

```
dycast.ts:1100  case ROOM_RANK: decodeRoomRankMessage(payload)
dycast.ts:1141  _getCastRanksB() → { nickname, avatar, rank: i+1 }
dycast.ts:1012  emitter.emit('message', messages)
store/index.ts:470  cast.on('message') → handleMessages(msgs)
store/index.ts:368  case ROOM_RANK: if (msg.rank?.length) state.rankGiftList = msg.rank
```

### 3.2 断点分析（已排除项 + 候选）

**已排除**：
- 字段名不匹配 → 不存在。`LiveRankItem{nickname,avatar,rank}` 与界面用字段完全一致。
- 空快照覆盖 → `store:370` 的 `if (msg.rank?.length)` 门槛意味着**空快照不会清掉旧数据**。所以"从有数据变成空"只可能来自下面 (A) 或 (B)，不可能来自"推了空榜"。
- 协议层没订阅过滤 → `dycast.ts` 对 `response.messages` 全量解码，服务端推什么解什么，无白名单。

**候选 (A)｜msgId 去重丢弃周期性快照 ← 头号嫌疑**

- `store/index.ts:334`　`if (!msg.id) continue;` → msgId 缺失时**整条丢弃**
- `store/index.ts:335-337`　`key = ${method}-${msg.id}` + `if (msgIdSet.has(key)) continue` → 同 method+id 第 2 次起丢弃
- **ROOM_RANK 是"榜单快照"而非事件**：服务端周期性整表重推，内容在变但**很可能复用同一个 msgId**（或干脆没有 msgId）。
  - `msgId` 缺失 → 全部死在 `:334` → 榜单永远为空
  - `msgId` 稳定复用 → 只有第一条能进，之后全被 `:336` 丢弃 → 榜单冻结（若第一条恰好是空榜，则永远为空）
- 旁证：`ROOM_USER_SEQ`/`ROOM_STATS`（`:361-367`）能刷新在线人数，说明**帧本身进得来**，问题出在"快照被 msgId 去重"这一层，而不是"根本没收到消息"。

**候选 (B)｜自动重连清空榜单 ← 新发现（确实存在的机制）**

- `store/index.ts:252-262` `clearMessages()` 里 `:260` `state.rankGiftList = []`
- 调用点只有 `connectLive` 开头（`:401`）
- 而 `scheduleAutoReconnect`（`:196-209`，`:207` 调 `connectLive`）+ `initAutoReconnect`（`:212-220`，回前台触发）
  → **每次"后台断连 → 自动恢复"都会把榜单清空**
- 叠加已知的"后台约 2 分钟断连"问题：重连后若服务端不立即补推非空快照，**或补推的快照被 (A) 去重丢弃**，界面就一直空。两个候选会互相放大。

### 3.3 修复方案

| 步骤 | 动作 |
|---|---|
| B1 | 把**状态快照类**消息（ROOM_RANK，建议连同 ROOM_USER_SEQ / ROOM_STATS）从 `store/index.ts:333-337` 的 id 校验与去重中**豁免** —— 它们是幂等的整表覆盖赋值，重复处理无副作用 |
| B2 | 或对快照类改用"内容指纹 + 时间窗口"去重（更保守，但实现更重） |
| B3 | **重连不清空榜单**：`connectLive` 里区分「用户主动切换房间」与「自动重连」；自动重连路径不清 `rankGiftList`（保留旧值直到收到新快照） |
| B4 | 加临时日志：收到 ROOM_RANK 时打印 `msgId / ranks.length`，实机跑一次判定是 (A) 里的哪种（缺失 vs 复用） |
| B5 | `LivePage.vue:24` 去掉 `item.rank === '-' ? '-' : i+1` 的死分支（`dycast.ts:1150` 保证 rank 恒为 i+1） |
| B6 | 后备：若日志证实 ROOM_RANK **根本不推送**，改用轮询接口获取榜单 |

**建议先做 B4 取一次日志**，确认 (A) 的具体形态后再落 B1/B2 —— B1 与 B2 二选一，不叠加。

## 4. P4｜通知每条消息都新建弹窗 → 改为"更新同一条"

### 4.1 证据（确定）

- `NotificationHelper.kt:67`
  `val id = payload.optInt("id", generateNotificationId(title, body))`
- `NotificationHelper.kt:216-218`
  `generateNotificationId()` 把 **`System.currentTimeMillis()`** 混进 hash → **每次调用必然唯一**
- `notificationManager.ts:355-381` `flush()` 调用 `postNotification()` 时 **从不传 `id`** → 100% 走随机 id 分支

**结论**：系统每次都认为是"新通知"，所以每条消息一个弹窗。这正是用户给的 Android 文档里说的"id 必须固定"。

### 4.2 修复方案（对齐用户提供的官方机制）

| 步骤 | 动作 |
|---|---|
| C1 | `flush()` 为每个类别分配**固定 id**：chat=2001 / gift=2002 / enter=2003 / follow=2004 / fansclub=2005 / like=2006，传给 `postNotification({ id })` → 系统覆盖同一条 |
| C2 | 每类别维护**滚动累积文本**（如最近 10 条或 500 字上限），更新时整体替换 body；标题带计数 `弹幕 (128)`，实现"实时刷新同一条" |
| C3 | 点赞类单独设 3–5s 合并窗口（复用已有 `mergeSeconds`，默认 5）+ 固定 id 2006 → 点赞 3-5 秒刷新一次，**只占 1 条通知** |
| C4 | `NotificationHelper.kt`：`generateNotificationId` 去掉 `currentTimeMillis`（改为 title+body hash 兜底）；新增 `setOnlyAlertOnce(true)`，首次响铃、后续更新**静默**，避免反复响铃/振动 |
| C5 | 汇总通知 `postSummaryIfNeeded()`(:198) 目前只创建一次、内容永不更新 → 改为每次刷新汇总文案（"礼物 3 · 弹幕 12"），**或直接移除**（需用户确认） |
| C6 | `clearAllNotifications()`(:141) 依赖 `postedIds`；固定 id 后 set 天然只剩 6 个，逻辑无需大改 |

### 4.3 效果对比

| 场景 | 现在 | 修复后 |
|---|---|---|
| 100 条弹幕 | 100 个通知 | 1 个通知，内容实时刷新 |
| 点赞刷屏 | 每个点赞 1 条 | 1 条，3-5s 刷新 |
| 通知栏占用 | 迅速淹没 | 最多 6 条（按类别） |

## 6. P6｜贡献榜无法上下滑动

### 6.1 证据

- `LivePage.vue:348-355`　`.rank-list { max-height:130px; overflow-y:auto; touch-action:pan-y; overscroll-behavior:contain }`
- `LivePage.vue:221-229`　父级 `.page-body { overflow-y:auto; display:flex; flex-direction:column }`
- 全局样式无 `touch-action` / `overflow` 禁用（已核 `style.css`、`assets/main.css`），无 `touchmove` 拦截

### 6.2 已排除 + 真正的差异点

**已排除**（逐项核查结果）：
- ❌ 全局样式拦截：`style.css` / `assets/main.css` / `index.html` / `App.vue` 全查，无全局 `touch-action`、无全局 `user-select` 禁用、无 JS `touchstart/touchmove/preventDefault`（全库仅 4 处 `touch-action`，都是本组件自己写的）
- ❌ `.rank-panel { flex-shrink:0 }` 把高度压没：`flex-shrink:0` 是"不收缩"，不会压扁容器
- ❌ 需要手动 touch 处理：没有 JS 抢手势，`touch-action:pan-y` 本身已允许纵向滑动

**真正的差异点（关键）**——对比 `CastListMobile.vue:54-61`：
| | `.cast-list`（能滚） | `.rank-list`（划不动） |
|---|---|---|
| 层级 | `.page-body` 的**直接子元素** | `.rank-panel` 内的**嵌套孙元素** |
| 高度来源 | `flex:1`（由 flex 父容器分配到**确定值**） | `max-height:130px`（依赖 WebView 对嵌套 max-height 滚动容器的实现） |

弹幕列表的滚动视口高度来自 flex 布局（确定 → 稳定），贡献榜来自 `max-height`（不确定 → 在 Android WebView 上可能形不成独立滚动视口）。

**另一个必须考虑的前提**：若 `rankGiftList` 为空或条数 ≤ 5（130px ÷ 单行约 26px），**本来就没有可滚动内容** —— 会被误判成"不能滑动"。所以 **P6 依赖 P3 先修**。

### 6.3 三个方案

**方案 A（推荐）——照抄可用的 `CastListMobile` 模式，让滚动视口由 flex 决定**
- `.rank-panel` 给确定高度：`flex: 0 0 160px`（或 `height:160px`）
- `.rank-list` 把 `max-height:130px` 改成 `flex:1; min-height:0;`（保留 `overflow-y:auto` 等）
- 滚动视口与弹幕列表**同源**，最稳

**方案 B —— 交给已经可用的整页滚动**
- 删除 `.rank-list` 的 `max-height` / `overflow-y`，榜单自然撑高，随 `.page-body` 一起滚
- 单层滚动 100% 可靠；代价是 `.rank-panel` 是 `flex-shrink:0`，会挤压下方 `.cast-list` 高度

**方案 C —— 防御性微调（最小改动）**
- `.rank-list` 加 `min-height:0`，并把 `max-height` 换成固定 `height`
- 保证一定存在"确定高度"的滚动框

### 6.4 附加：长昵称被截断（用户诉求是"查看用户名称"）

- `LivePage.vue:389-396` `.rank-name { white-space:nowrap; overflow:hidden; text-overflow:ellipsis }`
- 即使能滚动，**长昵称仍被省略号截断，看不全**
- 建议：去掉 `white-space:nowrap`，改为最多两行（`-webkit-line-clamp:2` + `word-break:break-all`）

> 建议：**方案 A + 6.4 昵称换行**，一并解决"划不动"和"看不全"。
